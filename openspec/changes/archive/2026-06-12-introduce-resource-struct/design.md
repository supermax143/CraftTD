## Context

В текущей архитектуре проекта Money и Food представлены как отдельные числовые значения (int/float) в различных классах. Это приводит к:
- Дублированию логики работы с ресурсами
- Отсутствию типобезопасности (можно случайно передать Money вместо Food)
- Сложности при добавлении новых типов ресурсов

Проект использует Unity с Zenject для DI. Ресурсы используются в моделях (EpochModel), контроллерах (GameController), UI и системах сохранения/загрузки.

## Goals / Non-Goals

**Goals:**
- Создать унифицированную сущность Resource с типизацией
- Обеспечить типобезопасность операций с ресурсами
- Упростить добавление новых типов ресурсов в будущем
- Заменить все использования Money и Food на Resource

**Non-Goals:**
- Изменение игровой логики или баланса
- Добавление новых типов ресурсов кроме Food и Money (только подготовка инфраструктуры)
- Изменение UI отображения ресурсов (только замена типов данных)

## Decisions

### Resource как struct вместо class
**Решение:** Использовать struct для Resource

**Обоснование:**
- Ресурсы - это простые значения, не требующие наследования
- Struct обеспечивает value semantics, что интуитивно для числовых значений
- Меньше аллокаций в куче, лучше производительность

**Альтернативы рассмотрены:**
- Class: избыточно для простых значений, дополнительные аллокации

### ResourceType как enum
**Решение:** Использовать enum для ResourceType

**Обоснование:**
- Типобезопасность на этапе компиляции
- Эффективное хранение (int)
- Легко расширять новыми значениями

**Альтернативы рассмотрены:**
- String: нет типобезопасности, ошибки опечаток
- Abstract class с наследниками: избыточно для простого перечисления

### Операторы для арифметики и сравнения
**Решение:** Перегрузить операторы +, -, ==, !=, <, > для Resource

**Обоснование:**
- Интуитивный синтаксис: resource1 + resource2
- Соответствует существующему коду с числовыми значениями
- Типобезопасность: операторы проверяют совпадение типов

**Альтернативы рассмотрены:**
- Методы Add/Subtract: менее читаемый код
- Extension методы: менее интуитивно

### Проверка типов в операторах
**Решение:** Бросать исключение при попытке операций над разными типами ресурсов

**Обоснование:**
- Явное указание ошибки в логике
- Fail-fast принцип
- Помогает обнаружить баги на ранних этапах

**Альтернативы рассмотрены:**
- Silent fail: скрывает ошибки
- Return default value: запутывает логику

## Risks / Trade-offs

### Risk: Обширные изменения в кодовой базе
**Описание:** Замена Money и Food затронет множество файлов

**Mitigation:** 
- Пошаговая замена по модулям
- Компилятор поможет найти все места использования
- Тестирование после каждого модуля

### Risk: Проблемы с сериализацией
**Описание:** Unity сериализатор может некорректно работать с struct

**Mitigation:**
- Проверить сериализацию Resource в Unity Inspector
- При необходимости добавить [Serializable] атрибут
- Тестировать сохранение/загрузку игры

### Trade-off: Производительность против типобезопасности
**Описание:** Проверка типов в операторах добавляет накладные расходы

**Обоснование:** Накладные расходы минимальны (простое сравнение enum), типобезопасность важнее

## Migration Plan

1. Создать Resource struct и ResourceType enum
2. Добавить операторы и методы для Resource
3. Заменить Money в моделях (начиная с EpochModel)
4. Заменить Food в моделях
5. Обновить контроллеры для работы с Resource
6. Обновить UI компоненты
7. Обновить системы сохранения/загрузки
8. Компиляция и исправление ошибок
9. Тестирование игры

**Rollback strategy:** Git commit после каждого этапа для возможности отката
