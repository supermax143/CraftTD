## Context

В текущей архитектуре игры юниты управляются через state machine с состояниями движения, атаки и другими поведениями. Отсутствует возможность временно переключать юниты в оборонительный режим, где они остаются на месте и атакуют только при приближении врагов.

Открытие юнитов по эпохам реализовано через EpochModel.OpenUnit с использованием GameStats для расчета стоимости и UnitEntity для атрибутов. Стоимость разблокировки (UnlockCost) формируется через GameStats.GetUnitOpeningCost и хранится в UnitEntity.UnitUnlockCostAttribute. Персистенция состояния разблокировки хранится в EpochStorageData.

Новая механика должна следовать тому же паттерну: покупка оборонительной стойки через EpochModel, стоимость через GameStats, атрибут в UnitEntity, персистенция в EpochStorageData.

Ограничения:
- Core.Application не должен зависеть от Unity-слоя
- State machine юнитов должен оставаться расширяемым
- Покупка способности должна персистироваться между сессиями
- UI должен быть доступен только во время боя

## Goals / Non-Goals

**Goals:**
- Добавить возможность покупки оборонительной стойки для юнитов определенного тира за кристаллы через EpochModel (по аналогии с OpenUnit)
- Добавить DefenseStanceCost атрибут в UnitEntity (по аналогии с UnlockCost)
- Добавить метод GameStats.GetDefenseStanceCost для расчета стоимости
- Реализовать state machine state для поведения юнитов в обороне (idle на месте, атака в радиусе)
- Создать UI для активации/деактивации способности во время боя
- Обеспечить персистенцию купленных способностей в EpochStorageData

**Non-Goals:**
- Изменение существующих state machine состояний юнитов (только добавление нового)
- Изменение механики боя или баланса юнитов
- Поддержка оборонительной стойки для отдельных юнитов (только по тиру)
- Визуальные эффекты при активации/деактивации стойки (только UI индикация)

## Decisions

### 1. Покупка через EpochModel.OpenDefenseStance

**Решение:** Добавить метод OpenDefenseStance в EpochModel по аналогии с OpenUnit.

**Обоснование:**
- Соответствует существующему паттерну открытия юнитов
- Переиспользование существующей логики проверки условий и списания кристаллов
- Единый источник правды для состояния эпохи и её возможностей
- Минимальные изменения в архитектуре

**Альтернативы:**
- Создать отдельный класс TierDefenseStanceAbility: дублирует логику EpochModel, усложняет архитектуру
- Использовать ShopConfig: не соответствует паттерну открытия юнитов, требует интеграции с магазином

### 2. DefenseStanceState как отдельный state

**Решение:** Создать новый state machine state для оборонительной стойки.

**Обоснование:**
- Соответствует существующей архитектуре state machine
- Позволяет легко переключаться между состояниями
- Изолирует логику оборонительного поведения

**Альтернативы:**
- Добавить флаг в существующие состояния: усложняет логику состояний, нарушает принцип state machine
- Использовать комбинацию состояний: увеличивает сложность переходов

### 3. Стоимость через GameStats

**Решение:** Добавить метод GetDefenseStanceCost в GameStats для расчета стоимости по эпохе и тиру.

**Обоснование:**
- Соответствует существующему паттерну GetUnitOpeningCost
- Централизованная логика баланса
- Возможность настройки стоимости через баланс-конфигурацию

**Альтернативы:**
- Хардкодить стоимость в UnitEntity: нарушает паттерн, усложняет балансировку
- Использовать ScriptableObject конфигурацию: не соответствует паттерну существующих атрибутов

### 4. Атрибут DefenseStanceCost в UnitEntity

**Решение:** Добавить DefenseStanceCostAttribute в UnitEntity по аналогии с UnitUnlockCostAttribute.

**Обоснование:**
- Соответствует существующему паттерну атрибутов юнита
- Стоимость доступна через UnitModel (как UnlockCost)
- Единый подход к атрибутам сущности

**Альтернативы:**
- Хранить стоимость отдельно в UnitModel: нарушает паттерн, усложняет архитектуру
- Вычислять стоимость динамически: не соответствует паттерну существующих атрибутов

### 5. UI для активации/деактивации

**Решение:** Создать отдельный UI компонент в Unity.Presentation с кнопками для каждого тира.

**Обоснование:**
- Отделение UI от бизнес-логики
- Возможность кастомизации внешнего вида
- Соответствие существующей архитектуре UI

**Альтернативы:**
- Интегрировать в существующий battle UI: может усложнить существующий UI, нарушает принцип единой ответственности

## Risks / Trade-offs

### Risk 1: Сложность интеграции с существующей state machine
**Риск:** Добавление нового state может потребовать изменений в существующих переходах между состояниями.

**Mitigation:**
- DefenseStanceState должен быть изолированным и не влиять на существующие переходы
- Использовать события или команды для переключения состояний
- Тестировать все сценарии переходов между состояниями

### Risk 2: Персистенция купленных способностей
**Риск:** Некорректная персистенция может привести к потере покупок или дублированию.

**Mitigation:**
- Использовать существующую систему персистенции магазина
- Добавить валидацию при загрузке сохранений
- Тестировать сценарии сохранения/загрузки

### Risk 3: Баланс игры
**Риск:** Оборонительная стойка может сделать игру слишком легкой или нарушить баланс.

**Mitigation:**
- Настроить стоимость способности в кристаллах через конфигурацию
- Ограничить доступность по эпохам (только после открытия юнитов)
- Тестировать баланс на разных этапах игры

### Trade-off 1: Гранулярность управления
**Trade-off:** Управление стойкой по тиру, а не по отдельным юнитам.

**Обоснование:** Упрощает UI и управление, соответствует механике открытия юнитов по эпохам. Недостаток: менее гибкое управление.

### Trade-off 2: Время реализации
**Trade-off:** Использование существующей системы магазина ускоряет разработку, но может ограничить кастомизацию в будущем.

**Обоснование:** Приоритет скорости и минимальных изменений. Если потребуется больше кастомизации, можно будет выделить отдельную систему позже.

## Migration Plan

1. Добавить метод OpenDefenseStance в EpochModel
2. Добавить свойство DefenseStance и методы в UnitModel
3. Добавить DefenseStanceCostAttribute в UnitEntity
4. Добавить метод GetDefenseStanceCost в GameStats
5. Расширить EpochStorageData для хранения состояния покупки оборонительной стойки
6. Создать DefenseStanceState и интегрировать в state machine
7. Создать UI компонент в Unity.Presentation
8. Интегрировать UnitController с оборонительной стойкой
9. Тестировать покупку, активацию/деактивацию и поведение юнитов

**Rollback strategy:** Удалить новые методы и вернуть существующие файлы к исходному состоянию через git.

## Open Questions

1. **Стоимость способности в кристаллах:** Требуется балансировка стоимости для каждого тира через GameStats. Предлагается начать с базовых значений (аналогично UnlockCost с коэффициентом) и настроить после тестирования.

2. **Визуальная индикация стойки:** Требуется ли визуальный эффект для юнитов в оборонительной стойке (например, изменение цвета или иконка)? Предлагается начать с UI индикации без визуальных эффектов на юнитах.

3. **Кулдаун активации:** Требуется ли кулдаун между активацией и деактивацией стойки? Предлагается без кулдауна для максимальной гибкости игрока.
